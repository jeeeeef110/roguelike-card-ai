# 設計文件:Roguelike 卡牌構築遊戲(v2.2 定稿 + v2.3 修正)

> 本文件為遊戲設計的唯一事實來源。開發進度與決策紀錄見 [PROGRESS.md](../PROGRESS.md)。

---

## 〇、最高設計原則

**不要增加更多內容,而是增加更多選擇。**
每張卡、每隻敵人、每個事件都必須讓玩家問自己一個問題(現在打還是留著?轉不轉流派?付不付這個代價?)。決策比運氣重要:**所有代價由玩家自己選擇承擔,不做純機率成敗卡。**

## 一、專案定位

- **類型**:單機 Roguelike 卡牌構築(DBG)+ 局外養成
- **技術棧**:Python 3 單一程式碼庫(core 純邏輯 / Pygame UI / headless 模擬器)
- **核心賣點**:
  1. MCTS 玩家代理(determinization 處理隨機),兼遊戲內建議與模擬器引擎
  2. 蒙地卡羅模擬驅動數值平衡,含 A/B 對照實驗
  3. core/ui/sim 分層:一套規則引擎同時支撐遊戲與模擬
  4. **卡牌設計與 AI 共同演化**:刻意埋入延遲收益、多回合規劃、出牌順序、資源交換等決策,讓三版代理拉開可量化的差距

## 二、不可推翻的決策

1. 敵人為腳本化意圖制(加權狀態機),不持有牌組
2. 代理三版演進並保留對照:規則式 → Expectimax → MCTS+UCB1
3. core 零依賴、RNG 注入 seed、同 seed 可重播
4. 選卡評估:啟發式 + 模擬驗證兩層
5. 平衡分析用 A/B 對照實驗
6. 不做:遺物、能力牌、多幕、複雜資源、純運氣卡
7. Payoff 不得指數成長(用「轉換清空」或上限設計)
8. 敵人干擾不得讓玩家「沒事做」(用加費/限制,不用剝奪行動)

## 三、戰鬥規則(定案)

### 3.1 回合結構
- 回合開始:抽 5 張、能量回滿 3 點(受修正效果影響)、格擋歸零(堅守效果除外)
- 出牌受能量限制;攻擊卡每回合上限 3 張(v2.3,「破限」可解除);回合結束手牌全棄
- 敵人回合開始宣告意圖(公開),回合結束執行
- 牌庫抽完 → 棄牌堆洗回(注入 RNG)

### 3.2 狀態效果(5 種)
| 狀態 | 機制 | 持續 |
|------|------|------|
| 護甲 | 抵銷等量傷害 | 回合開始歸零(堅守例外) |
| 力量 | 每層攻擊 +1(逐次攻擊各加成) | 該場戰鬥永久 |
| 易傷 | 受到傷害 ×1.5(向下取整) | N 回合,每回合 -1 |
| 中毒 | 回合開始扣層數等量 HP,無視護甲 | 每回合層數 -1 |
| 虛弱 | 攻擊傷害 -25%(向下取整)(v2.3) | N 回合,每回合 -1 |

**設計修正紀錄**:
- 原「賭命一擊」(50/50 機率)移除:純運氣不是決策 → 改為「透支」(代價確定、玩家自選、延遲成本考驗搜尋深度)
- 原「催化」(中毒 ×2 疊層)移除:指數成長難平衡 → 改為「引爆」(轉換並清空,payoff 自帶煞車,且產生「引爆時機」決策)
- 原「終結」(3 費 20 傷無條件)移除:與 build 無關 → 改為「制裁」(易傷 build 的條件收尾)
- v2.3(首次試玩後):玩家 HP 定為 50;攻擊卡每回合上限 3 張 + 新卡「破限」;
  新狀態「虛弱」+ 新卡「痺擊」(降敵傷的真空缺)

### 3.5 稀有度與取得
- 普通(權重 3)/ 稀有(權重 1);build 定義卡全為稀有
- 戰鬥勝利三選一;商店固定販售 1 稀有 + 刪卡服務(花錢定向湊 build)

## 四、敵人設計(定案)

每隻敵人 = 一道謎題,玩家看到敵人就要想「這隻怎麼打」。干擾一律用加費/條件限制,不剝奪玩家行動。

| 敵人 | HP | 意圖狀態機 | 被動特性(謎題) | 破解方式 |
|------|----|-----------|----------------|---------|
| 巨鼠 | 42 | 60% 攻擊 6 / 40% 蓄力→下回合攻擊 12 | 蓄力期間受到 ≥8 傷害則打斷(改普攻 6) | 爆發打斷 vs 疊甲硬吃 vs 痺擊減傷 |
| 毒蛛 | 33 | 50% 攻擊 4+中毒 2 / 30% 中毒 3 / 20% 護甲 6 | 每 3 回合織網:玩家下回合攻擊卡費用 +1 | 織網回合改打技能/防禦,或提前清手牌 |
| 石像兵 | 60 | 固定循環:護甲 8 → 攻擊 9 → 攻擊 9 | 每回合被動 +3 護甲,護甲不歸零 | 破甲、毒(無視護甲) |

(HP 為模擬平衡後數值,原 28/22/40:三代理勝率全 100% 飽和 → +50% 拉長戰鬥)

**Boss:腐化騎士(HP 90)**
- 狂暴計時:每 3 回合力量 +1(反龜縮——玩家必須在疊引擎與搶輸出間抉擇)
- 階段切換(HP < 50%):攻擊模式從單次重擊(9)變 3 連擊(5×3)——重擊怕高甲、連擊怕易傷反打,玩家中途必須調整防禦策略
- 數值經 36 組網格搜尋調校(原重擊 12/每 2 回合狂暴 → 起始牌組勝率 0%):
  目標「規則式代理勝率 25–40%」,定案組合實測 27.8%;
  同數值下 MCTS 89%、Expectimax 98%——Boss 是拉開代理差距的主要關卡(設計驗證)

## 五、地圖與事件(定案)

### 5.1 地圖(MVP:1 幕 10 層)
- 分層 DAG,每層 2–4 節點;約束:第 1 層必為一般敵人、第 9 層必為休息點、第 10 層 Boss、商店不連續
- 節點:一般敵人、休息點(回血 30%)、商店、問號事件

### 5.2 事件(服務 build 轉型,MVP 三個)
每個事件的核心問題:「我要不要正式轉流派?」

| 事件 | 選項 | 決策本質 |
|------|------|---------|
| 鐵匠 | 永久將一張卡費用 -1(最低 0)/ 離開 | 強化哪條路線? |
| 毒藥商 | 全部毒卡中毒值 +1,但失去一張非毒攻擊卡 / 獲得一張毒刃 / 離開 | 全押毒流的承諾 |
| 老戰士 | 移除一張防禦,換一張隨機攻擊卡 / 離開 | 犧牲穩定換輸出 |

## 六、AI 系統(定案)

### 6.1 三版玩家代理
1. 規則式:優先擋致死、再最大化即時輸出(**設計上會短視**)
2. Expectimax:深度 2–3,機率節點取樣(**能規劃幾步**)
3. MCTS+UCB1:determinization(**長期模擬找真最佳解**)

### 6.2 卡池刻意埋入的搜尋考驗
| 決策類型 | 代表設計 | 規則式 | Expectimax | MCTS |
|----------|---------|--------|------------|------|
| 延遲收益 | 蓄勢、蓄力、毒 | 低估 | 深度內可見 | rollout 捕捉 |
| 延遲成本 | 透支 | 忽略 | 能算到 | 能算到 |
| 引爆時機 | 引爆 | 手寫規則勉強 | 邊界深度吃力 | 主場 |
| 出牌順序 | 撕裂、破甲→反甲擊、順勢斬 | 固定優先序出錯 | 組合爆炸吃力 | 樹搜尋天然處理 |
| 牌庫知識 | 回收、兵法時機 | 不建模 | 不建模 | determinization 主場 |
| 打斷閾值 | 巨鼠蓄力 | 需手寫 | 能算 | 能算 |
| 條件收尾 | 制裁、易傷窗口 | 部分 | 能算 | 能算 |

預期產出:三版代理分別在 5 條 build 牌組下的勝率矩陣 + 決策時間。

### 6.3 選卡評估與平衡
- 選卡:啟發式評分 + 模擬驗證(N 場勝率比較)
- 平衡:headless 1000+ 場;A/B 對照實驗(固定代理與基準牌組、單一變因)歸因卡牌強度;調整前後圖表存檔

## 七、技術架構

```
project/
├── core/     # GameState、卡牌效果、敵人意圖、事件。零依賴、seed 可重現
├── agents/   # rule_based / expectimax / mcts,介面 Agent.choose_action(state)
├── ui/       # 終端對戰 + Pygame(規劃中),只呼叫 core 公開 API
├── sim/      # 模擬器、A/B 實驗、統計輸出
└── tests/    # pytest
```
- 效果類型:延遲觸發(蓄勢/堅守/透支)、回合內計數(撕裂/攻擊上限)、狀態轉換(引爆)、費用修正(織網)、意圖打斷(巨鼠)——全部落在「效果=資料 + 事件鉤子」框架內
- commit 格式 `[模組] 做了什麼`;README 記錄設計決策與失敗嘗試

## 十、風險與退路

- 進度落後 → 砍內容(事件、卡牌數),絕不砍代理與模擬器
- MCTS 失敗 → 凍結在 Expectimax,對照敘事仍成立
- 模擬太慢 → 降 rollout、`__slots__`、避免 deepcopy;瓶頸寫進報告
- 效果鉤子系統過度設計 → 只實作 MVP 需要的鉤子,不做通用框架
