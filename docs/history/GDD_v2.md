# GDD v2:Roguelike 卡牌構築遊戲(APCS 備審專案)

> v1 → v2 修正摘要:敵人改為腳本化意圖制;MCTS 移至玩家側代理(兼模擬器引擎與遊戲內建議);技術棧統一為 Python 單一程式碼庫(core/ui/sim 三層);牌組評估改為「啟發式 vs 模擬驗證」;平衡分析加入 A/B 對照實驗;時程重心前移至暑假。

## 一、專案定位

- **類型**:單機 Roguelike 卡牌構築(DBG)+ 局外養成
- **技術棧**:Python 3(core 純邏輯 / Pygame UI / headless 模擬器,單一程式碼庫)
- **核心賣點(備審視角)**:
  1. MCTS 玩家代理:在隨機抽牌的不完全資訊下做決策
  2. 蒙地卡羅模擬驅動的數值平衡(含 A/B 對照實驗)
  3. core/ui/sim 分層架構:一套規則引擎同時支撐遊戲與模擬
- **一句話描述**:玩家在隨機生成的地圖中對抗意圖制敵人、構築牌組、養成角色;遊戲內建一個會思考的 AI 代理,既能給出牌建議,也被用來自動測試遊戲平衡。

## 二、核心循環

```
選擇地圖節點 → 戰鬥 / 事件 / 商店 → 獲得卡牌與資源
→ 強化牌組 → 挑戰頭目 → 局外養成(解鎖角色/卡池)→ 下一輪
```

## 三、系統設計

### 3.1 戰鬥系統

- 回合制:玩家出牌階段 → 敵人執行意圖
- 資源:每回合 3 點能量,卡牌消耗能量
- 卡牌類型:攻擊 / 防禦 / 技能(buff、抽牌、能量操作)
- 狀態效果:中毒、易傷、護甲、力量(MVP 各 1 種)

**敵人設計:腳本化意圖系統(v2 修正)**
- 敵人不持有牌組,每回合依行為模式宣告意圖(攻擊 X 點 / 防禦 / 施加狀態),玩家可見
- 行為模式:加權狀態機(例:巨鼠 = 60% 攻擊、40% 蓄力後重擊)
- 設計理由:符合類型慣例、玩家可做資訊決策、實作與平衡成本低
- 面試素材:為什麼「敵人簡單、玩家側 AI 複雜」是正確的複雜度分配

### 3.2 MCTS 玩家代理(演算法主戰場,v2 修正)

一個會玩這款遊戲的 AI,扮演玩家側,兩個用途:
- **遊戲內**:「出牌建議」功能(顯示代理認為的最佳動作與勝率估計)
- **遊戲外**:平衡模擬器的引擎(見 3.5)

**演進路線(保留三版對照)**:
1. 規則式代理(基準線:優先擋致死傷害,再最大化輸出)
2. Expectimax(深度 2–3;抽牌隨機性以機率節點取樣建模,說明分支爆炸與取樣的取捨)
3. MCTS + UCB1(隨機性以 determinization 處理:每次 rollout 洗一副假想牌庫)

面試素材:三版代理在固定敵人配置下的勝率對照表 + 每步決策時間比較。

### 3.3 牌組構築系統

- 起始牌組 10 張,戰鬥後三選一加牌,商店可刪牌
- **選卡評估(v2 修正,原「貪婪 vs DP」不成立)**:
  - 第一層:啟發式評分函數(能量曲線、攻防比例、與現有卡的 combo 觸發率)
  - 第二層:模擬驗證——把候選卡加入牌組,用 MCTS 代理各跑 N 場,直接比勝率
  - 面試素材:啟發式(快但近似)vs 模擬(準但貴)的取捨,以及兩者結論不一致的案例分析

### 3.4 地圖生成

- 節點式地圖:分層 DAG,MVP 10 層、每層 2–4 節點
- 加權隨機 + 約束(商店不連續、頭目前必有休息點)+ 連通性檢查

### 3.5 平衡性分析(大加分項,v2 強化)

- headless 模擬器:MCTS 代理自動打完整局,1000+ 場
- 基礎統計:卡牌採用率、平均戰鬥回合數、各層存活率
- **A/B 對照實驗(v2 修正)**:固定代理與基準牌組,單一變因換卡,比較勝率差
  - 理由:直接統計卡牌勝率貢獻有混淆變數(強代理配什麼都贏);對照實驗才能歸因
- 用數據迭代數值,保留調整前後對照圖表
- 面試素材:「相關不等於因果,所以我設計了對照實驗」

### 3.6 養成系統(局外)

- 貨幣:每局結算獲得靈魂碎片
- 用途:解鎖角色(不同起始牌組)、擴充卡池、永久小幅加成
- 存檔:JSON 本地存檔

## 五、技術架構(v2 修正:單一程式碼庫)

```
project/
├── core/     # 純邏輯:規則引擎、卡牌效果、敵人意圖、狀態機
│             # 零外部依賴、完全確定性(RNG 注入 seed)
├── agents/   # 規則式 / Expectimax / MCTS 代理
├── ui/       # Pygame 介面,只呼叫 core 的公開 API
├── sim/      # headless 模擬器、A/B 實驗、統計輸出(matplotlib)
└── tests/    # core 的單元測試(pytest)
```

- **RNG 注入 seed**:同一 seed 可重播整場戰鬥——除錯利器,也是模擬可重現性的關鍵,面試可講
- **版本控制**:GitHub,commit 認真寫,README 記錄設計決策與失敗嘗試
- **效能退路**:MCTS rollout 過慢時,先做狀態複製最佳化(`__slots__`、避免 deepcopy),再考慮局部改寫

## 六、開發時程(v2 修正:困難的事全部塞進暑假)

### 第一階段:core + 代理 + 模擬器(7 月,4 週)★整個專案的技術核心
- W1:core 規則引擎 + 敵人意圖系統 + pytest(純終端可跑完整戰鬥)
- W2:規則式代理 + headless 模擬器雛形(能自動打完一場並輸出 log)
- W3:Expectimax 代理 + 隨機性建模
- W4:MCTS 代理 + 三版對打數據第一批

### 第二階段:遊戲化(8 月,4–5 週)
- W5-6:Pygame UI(手牌、出牌、敵人意圖顯示)
- W7:地圖生成 + 完整一輪流程串接
- W8-9:25 張卡 + 3 敵人 + 頭目,MVP 可玩;A/B 平衡實驗第一輪

### 第三階段:低耗能收尾(9–11 月,開學後每週約 5 小時)
- 9 月:養成系統、存檔
- 10 月:數值迭代(跑模擬 → 調數值,零散時間就能做)
- 11 月:修 bug、錄 demo 影片、README 補完 → **凍結**

### 第四階段:學測衝刺(12–1 月)
- 停止開發。

### 第五階段:備審整理(2–3 月)
- 小幅擴充(第二角色)
- 專案報告:架構圖、代理演算法演進、A/B 平衡圖表
- 面試 QA 演練:每個決策都要能答「為什麼、還試過什麼」

## 七、風險與退路

- **進度落後**:砍內容量(卡牌、敵人數),絕不砍代理與模擬器
- **MCTS 做不出來**:退守 Expectimax,對照敘事仍成立
- **Python 模擬太慢**:降 rollout 次數 + 狀態複製最佳化;報告誠實寫效能瓶頸與對策(這反而是好素材)
- **暑假進度不如預期**:第一階段結束時檢查點——若 W4 底 MCTS 未成,直接凍結在 Expectimax,把時間讓給遊戲化

## 八、備審敘事主軸

1. 動機:做一個「內建會思考的 AI」的卡牌遊戲
2. 架構:core/ui/sim 分層——為什麼規則引擎必須與 UI 解耦
3. 挑戰一:隨機抽牌下的決策 → 規則式 → Expectimax → MCTS(determinization)
4. 挑戰二:平衡難調 → 蒙地卡羅模擬 → 發現混淆變數 → A/B 對照實驗
5. 成果:代理勝率對照、平衡前後數據、可玩 demo
6. 反思:取捨與未竟之處(誠實寫)
